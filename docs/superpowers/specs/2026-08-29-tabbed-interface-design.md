## 1. Контекст и проблема

`dispatcher/server/static/index.html` — одна страница на 4496 строк, где
пятнадцать секций уложены в вертикальный отчёт. Чтобы ответить на один вопрос,
оператор прокручивает мимо всех остальных подсистем. Discovery-бриф называет это
FR-02 с приёмкой «ни один экран не смешивает темы», и он же фиксирует более
резкий факт: инструментом сегодня не пользуются (G-03).

Launchpad (PR-C, #209, merge `a58fb30`, 2026-08-27) ситуацию обострил. Он —
корневая панель по замыслу спеки §9 и по факту разметки (`index.html:153`), но
лежит в том же вертикальном свитке: главный операторский экран отделён от
второго по важности (`Sync`) секцией `Unresolved task requests`, а от run
view — четырьмя другими. Жизненный цикл запуска — Ready → Pending launches →
Active → Recent completed → подробности прогона — читается прокруткой.

Ровно один общий таймер (`setInterval(refresh, 10000)`, `index.html:3774`)
дёргает восемь endpoint'ов в одном `Promise.all` независимо от того, на что
смотрит оператор. Launchpad уже завёл собственный таймер на 30 с
(`LP_REFRESH_MS`, `index.html:3795`) — два независимых цикла на одной странице
существуют и сейчас.

## 2. Область и не-цели

### Входит

1. Верхняя tab-навигация на девять экранов и hash-роутинг.
2. Главный экран Launchpad: перенос `#launchpad` и `#run-console` в один
   tabpanel, run view как drill-down, manual-форма как свёрнутый блок.
3. Разделение монолитного `refresh()` на загрузчики экранов + опрос только
   активного экрана (с одним названным исключением, §9).
4. Экран Projects: список каталогов слева, полный README справа; новый
   read-only endpoint README.
5. Перекомпоновка Sync без смены источника истины.
6. Адаптация тестовой среды: `tests/web/dom.js` и все девять harness'ов (§10).

### Не входит

- Бизнес-логика Launchpad/Run console, их wire-контракты и DOM-id: переносятся
  контейнеры и точка входа, не поведение.
- Семантика Errors, Models, Contracts, Epics, Waits, Roadmap.
- Новый рантайм-вызов GitHub API из dispatcher или браузера.
- Удаление backend'ов Project detail, merge gate, task authoring, spec-runner
  config, Benchmarks — исчезают только их UI-входы (§6.3).
- Markdown-рендерер для README (§6.2).
- TUI, VSCode-расширение, MCP: поверхности паритета в этой работе не меняются,
  потому что не меняется ни одна модель данных, которую они читают.

## 3. Продуктовые решения

### 3.1. Девять вкладок, Launchpad первый

Порядок слева направо: `Launchpad`, `Sync`, `Projects`, `Errors`, `Models`,
`Contracts`, `Epics`, `Waits (partial)`, `Roadmap`. По умолчанию открыт
`Launchpad`.

`Run console` в списке отсутствует намеренно: он не предметная область, а
инструмент внутри Launchpad (§3.2). Верхняя навигация остаётся навигацией по
разделам системы и не смешивает разделы с отдельными операциями.

**Десятая, условная вкладка — `Benchmarks`.** Черновик воркспейса её не
упоминал, но секция `#benchmarks-section` существует и сегодня показывается
ровно тогда, когда eco-профиль сконфигурирован: `renderBenchmarks` снимает
`hidden` при `report.status !== "unconfigured"` (`index.html:539-541`). Она
никуда не помещается без насилия — это не Sync, не Roadmap и не Epics, — и
глотать её внутрь чужого экрана значит смешивать темы вопреки FR-02. Правило:
вкладка `Benchmarks` встаёт последней и присутствует в tablist **тогда и только
тогда**, когда endpoint отвечает не `unconfigured`, — та же видимость, что у
секции сегодня, поднятая на уровень навигации. На неcконфигурированном стенде
владелец видит ровно девять вкладок. Если benchmark-профиль сконфигурирован, а
активной была вкладка `Benchmarks`, и профиль пропал — экран падает на
`Launchpad`.

### 3.2. Run console — вложенный инструмент, не вкладка

Ready, Pending launches, Active и Recent completed — фазы одного жизненного
цикла запуска, а подробности прогона — их детализация. Отдельная вкладка
разрезала бы сценарий по границе навигации и заставила бы оператора переключать
экран посреди одного действия.

Следствия, обязательные к соблюдению:

- всё, что живёт в `#run-console` — submit, receipt, run view, verbs,
  resolution, ссылка на логи — сохраняет DOM-id, wire и свои тесты;
- вход в run view — drill-down из Launchpad (§5.3) плюс поле «Open run» внутри
  Manual (advanced) для диагностики по известному `request_id`;
- Manual (advanced) — свёрнутый блок внизу Launchpad, а не самостоятельный
  экран: launchpad-спека §9 требует, чтобы у authority и admission была ровно
  одна дверь.

Прямой ссылки на отдельный экран run console больше нет. Это изменение
доступности UI, и его нужно назвать в PR явно, а не выдать за перестановку DOM.

### 3.3. Один экран — один tabpanel

Под «одним экраном» понимается один корневой `tabpanel`. Внутри допустимы
таблицы, фильтры и локальные детали, уже принадлежащие разделу. Остальные
панели несут `hidden` и не занимают место в layout.

Единственное исключение — существующая глобальная полоса
`Unresolved task requests` (`#ta-outcomes`): исход отправленной мутации не
уничтожается переключением вкладки. Она остаётся над активным экраном до
закрытия или до отдельного решения о судьбе старого task-authoring UI.

Незакрытая попытка запуска (`Pending launches`) второй такой полосы **не**
получает: она остаётся подразделом Launchpad, а её невидимость с других вкладок
компенсируется правилом опроса §9.1, а не ещё одним глобальным элементом.

## 4. Контракт tab shell

```text
Dispatcher                                      updated 12:34:56
[Launchpad] [Sync] [Projects] [Errors] [Models] ... [Roadmap]
----------------------------------------------------------------
|                    active tabpanel only                      |
----------------------------------------------------------------
```

- контейнер `role="tablist"`; кнопки `role="tab"` с `aria-selected` и
  `aria-controls`; панели `role="tabpanel"` с `aria-labelledby`;
- Left/Right перемещают фокус, Enter/Space открывают экран;
- активная вкладка отличима не только цветом (нижняя граница/фон +
  `aria-selected`);
- на узкой ширине строка вкладок прокручивается горизонтально, названия не
  переносятся; таблицы сохраняют собственный `overflow-x`.

### 4.1. Роутинг

Экран хранится в hash: `#launchpad`, `#sync`, `#projects`, … Перезагрузка,
Back/Forward и прямая ссылка восстанавливают экран. Неизвестный hash безопасно
приводит к `#launchpad`.

Два экрана имеют вложенное состояние, и оно тоже в hash:

- `#launchpad/<request_id>` — открытый drill-down на прогон;
- `#projects/<directory>` — выбранный проект.

Грамматика вложенного сегмента закрытая: `#<screen>` или `#<screen>/<value>`,
где `value` — `[A-Za-z0-9._-]{1,200}`. Всё остальное — неизвестный hash.
Значение сегмента **никогда** не попадает в `innerHTML` и не используется для
построения пути на сервере иначе, чем через уже существующие endpoint'ы с их
собственной валидацией.

## 5. Экран Launchpad (главный)

### 5.1. Состав

| Блок | DOM | Роль |
|---|---|---|
| store banner | `#lp-store-banner` | `store_unreadable` и только он — не транспортная ошибка |
| Repositories | `#lp-repos` | `admission` + типизированные `blockers[]` |
| Ready | `#lp-ready` | строки, готовые к запуску, с two-step confirm |
| **Pending launches** | `#lp-pending` | попытки, которые ещё не разрешились |
| Active | `#lp-active` | живые прогоны |
| Recent completed | `#lp-recent` | терминальные исходы |
| Manual (advanced) | `#run-console` | свёрнутая форма `repo_key`/`work_id` + «Open run» |
| Diagnostics | `#lp-diagnostics` | нечитаемое как названный факт, без действий |

### 5.2. Pending launches

Подраздел существует потому, что попытка запуска переживает исчезновение своей
Ready-строки: ответ мог потеряться до того, как запись стала видна снапшоту.
Строка здесь — не ошибка и не красный статус, а третье состояние «исход
неизвестен» с Retry тем же `request_id` и read-back'ом
`GET /api/runs/{request_id}` (slice-0 §5.2, launchpad §9).

Перенос во вкладку не имеет права ослабить ни одно из свойств:

- запись живёт в `lpState.pending` вне DOM и не привязана к присутствию
  репозитория в последнем снапшоте (orphan-ветка рендера `#lp-pending`);
- пока попытка не разрешилась, свежий Launch для этой строки заблокирован;
- запись очищает только определённый HTTP-ответ; полный refetch снапшота сам по
  себе неизвестность не разрешает.

### 5.3. Drill-down на прогон

Клик по строке в Pending launches, Active или Recent completed раскрывает run
view внутри того же tabpanel: соседняя вкладка не открывается, текущий экран не
теряется. Выбранный прогон отражается в `#launchpad/<request_id>`.
Незалинкованные прогоны (`run_id` без `request_id`) drill-down не дают и ссылки
на логи не показывают — как сегодня.

### 5.4. Что обязано пережить перенос дословно

1. Типизированные цели блокеров: `launch_busy`/`run_in_flight` с `request_id` →
   run view; unlinked `run_in_flight` → идентификатор и статус, без ссылки;
   `run_vanished` → форма acknowledge; `lock_malformed` → форма
   release-malformed; `lock_io_unreadable`/`run_state_unreadable` →
   диагностический текст без действия.
2. Two-step confirm: клик раскрывает «Launch `<work_id>` @ `<sha7>`?
   [Confirm]», Confirm отправляет submit v2.
3. Ре-валидация раскрытого подтверждения после каждого refetch: если строка
   вышла из Ready, получила блокер или сменила `seen_revision` —
   типизированное состояние сохраняется, Confirm отключается с показанной
   причиной.
4. Transport-uncertainty как состояние строки, а не ошибка (§5.2).
5. Client request-sequence как единственный сторож устаревания: `snapshot_id`
   непрозрачен и неупорядочен; `inflight` — счётчик, не флаг.
6. 409 → текст из `code` + `current` и целиковый refetch, без вклеивания.
7. Обе escape-формы с предикатами, подтверждением и полями аудита.
8. Manual (advanced) молча подставляет `snapshot_id`/`seen_revision` текущего
   снапшота и проходит ту же admission.

### 5.5. Жизненный цикл при переключении вкладок

Переключение вкладки **скрывает** DOM Launchpad, но не пересоздаёт его:
`lpState` (`pending`, сообщения строк, escapes, sequence) переживает уход и
возврат.

Раскрытое подтверждение при этом **не** восстанавливается безусловно. На
возврате оно проходит ту же ре-валидацию §5.4.3 против актуального снапшота:
изменились данные, блокеры или `seen_revision` — подтверждение сбрасывается
либо обновляется по существующему контракту two-step confirm. Переживает
состояние, а не разрешение действовать.

## 6. Экран Projects

### 6.1. Контракт данных

`GET /api/overview` остаётся источником списка, но `OverviewEntry` получает
явное поле `directory` (сегодня клиент вычисляет каталог из basename `path` —
`mgDirBasename(p.path)`, `index.html:1958`; идентичность каталога не должна
выводиться на клиенте ни из display-name, ни из локального абсолютного пути).

Новый read-only endpoint:

```text
GET /api/projects/{directory}/readme
```

```jsonc
{
  "directory": "dispatcher",
  "state": "read",              // read | missing | unavailable
  "filename": "README.md",
  "content": "# Dispatcher\n…",
  "updated_at": "2026-08-29T10:00:00Z",
  "detail": null
}
```

`missing` — README действительно нет; `unavailable` — каталог/файл нельзя
безопасно прочитать, содержимое не UTF-8 или превышает лимит. Ни одно из этих
состояний не превращается в пустую строку и не выдаёт себя за прочитанный
пустой README (NFR-02 брифа).

Безопасность:

- `directory` резолвится только через уже обнаруженный/сконфигурированный
  проект; неизвестный каталог — 404, а не попытка чтения;
- запрет `..`, абсолютных путей и выхода по symlink за корень проекта;
- отдаётся только README из закрытого набора имён `core/descriptions.py`
  (`README.md`, `README.rst`, `README`, без учёта регистра);
- лимит размера — тот же `_MAX_SOURCE_BYTES` (256 KiB), что уже действует в
  `core/descriptions.py`; превышение — `unavailable`, не обрезанный текст;
- абсолютный локальный путь в ответе не возвращается;
- endpoint ничего не пишет и в сеть не ходит.

### 6.2. Отображение

Левая колонка — только имена каталогов, по одному в строке, алфавитно. Правая —
имя файла, состояние/freshness и полный текст README как текст в
прокручиваемом `<pre>`: без исполнения HTML и без второго Markdown-рендерера в
проекте. Это сознательный первый срез; красивый рендер — отдельное решение.

- первый доступный каталог выбирается при первом открытии вкладки;
- выбор отражается в `#projects/<directory>`;
- на узкой ширине список становится верхней полосой/`select`, README ниже;
- повторный выбор берёт кэш до общего refresh или явного Reload;
- поздний ответ проекта A не имеет права перерисовать выбранный проект B
  (generation token).

### 6.3. Судьба старого Project detail

Onboarding, governance, product proposals, orchestration runs, merge gate, task
authoring и spec-runner config **не** переносятся в новый Projects: иначе
требование «Projects = список + README» не выполняется. Backend и код этих
функций не удаляются — убираются их UI-входы. Возврат операций — отдельное
решение (например, экран `Actions` или контекстные действия внутри Launchpad).

Это самое крупное изменение доступности в работе, и оно должно быть названо в
PR первой строкой, а не обнаружено ревьюером.

## 7. Экран Sync

Источник истины не меняется:

```text
github-checker snapshot --local-only ─┐
                                      ├─ SyncService → /api/sync → Sync screen
published snapshots двух машин ───────┘
```

Сырой JSON `github-checker` в браузер не транслируется: это связало бы UI с
внешним контрактом и создало бы вторую реализацию нормализации рядом с
`SyncService`.

Верх экрана: общий verdict текущей машины; причина худшего verdict; время
живого замера и freshness опубликованных снимков; явный статус источника каждой
машины (`live`, `published`, `stale`, `unavailable`).

Основная часть: обе машины отдельными host-панелями или переключателем host;
внутри — одна строка на каталог репозитория с полями каталог, branch,
ahead/behind, dirty, состояние чтения, причина/ошибка, freshness. Существующие
действия и tracking proposals остаются рядом со своим репозиторием и не
становятся глобальными кнопками. Отсутствующий и непрочитанный репозиторий
визуально отличаются от clean/zero.

Работать на существующих `/api/sync` и `/api/sync/hosts`. Менять API только
если нужное поле уже есть в нормализованной модели, но теряется в ответе. Полей
«на всякий случай» не добавлять.

## 8. Экраны без изменения содержания

`Errors`, `Models`, `Contracts`, `Epics`, `Waits (partial)`, `Roadmap` и
условный `Benchmarks` (§3.1) переносятся во вкладки без изменения поведения, разметки внутри панели и
семантики. Отдельно фиксируется: перенос Epics не имеет права вернуть общий
«уверенный total» вместо `partial/unavailable`; слово `partial` у Waits —
состояние данных, а не обещание полноты; ошибка `/api/waits` по-прежнему
очищает старое содержимое и остаётся видимой; Roadmap — один tabpanel с двумя
представлениями одной read-model.

## 9. Загрузка и обновление

Вводится реестр экранов: `screen id → load() → render() → refresh policy`.

- при открытии вкладки — немедленная загрузка её данных;
- периодический refresh — только для активного экрана;
- каждый экран ловит и показывает собственную ошибку; независимый сбой одного
  endpoint не пустошит соседнюю вкладку;
- переключение экрана инвалидирует поздние ответы прошлого там, где они могут
  менять общий DOM;
- существующие специализированные guards (`waitsInFlight`, рендер ошибки Epics,
  Launchpad sequence/idempotency) сохраняются;
- скрытые экраны не очищаются при переключении: возврат не мигает пустотой, но
  состояние помечается как обновляющееся;
- `updated` показывает время обновления активного экрана, а не последнего
  случайного ответа любого endpoint.

**Названная межэкранная зависимость данных.** Колонка `Contract` в Roadmap
строится из ответа `/api/contracts` (`syncByName`, `index.html:2005-2013`), а не
из `/api/roadmap`. Разделение загрузчиков не имеет права её потерять: загрузчик
Roadmap запрашивает **оба** endpoint'а — `/api/roadmap`, `/api/roadmap/summary`
и `/api/contracts`. Экран `Contracts` при этом остаётся владельцем своей
таблицы; общего кэша между экранами не заводим — два запроса к одному
endpoint'у с разных экранов дешевле неявной связи через глобальную переменную.

### 9.1. Единственное исключение — Launchpad

Скрытый Launchpad продолжает опрашивать `/api/launchpad`, **пока в
`lpState.pending` есть незакрытая попытка**, и прекращает фоновый опрос сразу
после терминального результата или снятия uncertainty. Иначе «launch outcome
unknown» тихо замирает, пока оператор смотрит другой экран — ровно то
состояние, которое терять нельзя.

Глобальной полосы-уведомления при этом не вводим (решение владельца,
2026-08-29): цена — незакрытая попытка не видна с других вкладок до
возвращения; выигрыш — на экране не заводится второй глобальный элемент.

`/api/launchpad` опрашивает ровно один таймер — таймер Launchpad; общий refresh
его не дублирует.

## 10. Тестовая среда: почему перенос не механический

Это не побочная деталь реализации, а причина, по которой Фаза «каркас вкладок»
дороже, чем выглядит. Девять harness'ов (`tests/web/*_harness.js`) исполняют
**весь настоящий `<script>` страницы** в Node VM поверх `tests/web/dom.js`. Два
свойства этой среды вступают в конфликт с вкладками:

1. **`dom.js` не реализует `location`, `history` и `hashchange`.** Песочница
   harness'а даёт `document`, `console`, `URL`, таймеры, `fetch` и
   `window = {open(){}}` (`launchpad_harness.js:192-203`). Роутер, безусловно
   читающий `location.hash`, уронит на boot все девять harness'ов.
2. **`dispatch()` отказывается кликать по невидимому элементу**: `el.visible`
   обходит предков и учитывает `hidden` (`dom.js:211-240`). Как только панели
   получают `hidden`, каждый harness, который кликает вне активной вкладки,
   перестаёт работать — это Epics, Governance, Benchmarks, Runs, Run console,
   Run status, Task authoring, Product proposals.

Решение принимается на стороне среды, а не приложения:

- `dom.js` получает стабы `location` (с записываемым `hash`), `history`
  (`pushState`/`replaceState`, обновляющие `location.hash`) и доставку события
  `hashchange`. Это реализация браузера, а не правила dispatcher, — ровно то,
  для чего файл существует («implements the *browser*, never the
  application», `dom.js:5-9`);
- harness'ы получают общий хелпер открытия экрана (`openScreen(page, id)`),
  который переключает вкладку через **настоящую** кнопку страницы, а не
  выставляет `hidden` руками. Harness, снимающий `hidden` в обход UI,
  доказывает не то поведение, которое поставляется;
- страница читает `location` через feature-detect в том же идиоме, что уже
  применён к таймерам (`if (typeof setInterval !== "function") return;`,
  `index.html:4213`): без `location` роутинг деградирует до статичного
  `Launchpad` и не бросает.

Никакой harness не переписывает бизнес-проверки соседа: harness вкладок
проверяет навигацию и жизненный цикл, существующие harness'ы остаются authority
для внутреннего поведения своих блоков.

## 11. Тестовая стратегия

### API

- README: `read` для каждого имени из закрытого набора и для разного регистра;
  `missing`; non-UTF-8 → `unavailable`; превышение лимита → `unavailable`;
  неизвестный каталог → 404; traversal и symlink-выход не читают ничего;
  display-name ≠ directory; в ответе нет абсолютного пути.
- `OverviewEntry.directory` присутствует и берётся из чекаута/манифеста.
- Существующие endpoint'ы отвечают как раньше.

### Web harness

- при загрузке без hash открыт `Launchpad`;
- одновременно видим ровно один tabpanel; вызывается только его loader;
- прямой hash, Back/Forward, неизвестный hash → `#launchpad`;
- ARIA-связи и клавиатурная навигация;
- независимый сбой одного endpoint не ломает другую вкладку;
- уход с Launchpad и возврат не теряют `lpState.pending`: строка «launch
  outcome unknown» на месте, Retry всё ещё шлёт тот же `request_id`;
- раскрытое подтверждение после возврата: неизменившийся снапшот — форма как
  была; ушедшая из Ready строка, новый блокер или другой `seen_revision` —
  Confirm отключён с причиной, типизированное состояние сохранено;
- скрытый Launchpad с незакрытым pending продолжает опрашивать
  `/api/launchpad`, а после терминального ответа перестаёт;
- `/api/launchpad` не опрашивается вторым таймером;
- клик по Pending/Active/Recent открывает run view внутри Launchpad и
  проставляет `#launchpad/<request_id>`; unlinked-строка drill-down не даёт;
- README отрисован как текст: `<script>` в README остаётся текстом;
- быстрый выбор A→B с ответом B→A оставляет B;
- Sync с двумя hosts показывает обе машины; `unavailable/stale/no data` не
  становятся clean/zero.

### Ручная визуальная приёмка

1440 px и 390 px; длинные имена каталогов и README с длинной строкой; тёмная и
светлая схема; клавиатурная навигация по вкладкам; прямые ссылки на каждый
hash; обе машины на Sync, включая stale/unavailable; README missing/unavailable;
Launchpad с активным pending/unknown при уходе и возврате, включая раскрытое
подтверждение над изменившейся строкой; drill-down на прогон и возврат по Back.

## 13. Критерии приёмки

1. Вверху видны девять вкладок в согласованном порядке; первая — `Launchpad`,
   и она открыта по умолчанию. Десятая, `Benchmarks`, присутствует тогда и
   только тогда, когда eco-профиль сконфигурирован (§3.1).
2. Одновременно виден ровно один tabpanel.
3. Прямая ссылка и Back/Forward восстанавливают экран, включая
   `#launchpad/<request_id>` и `#projects/<directory>`.
4. Launchpad показывает Repositories, Ready, Pending launches, Active, Recent
   completed, Manual (advanced) и Diagnostics; run view открывается drill-down'ом
   изнутри; отдельной вкладки `Run console` нет.
5. Перенесённый Run console сохраняет все текущие wire/state/idempotency тесты.
6. Уход с Launchpad и возврат не теряют незакрытую попытку; раскрытое
   подтверждение возвращается только после ре-валидации против актуального
   снапшота.
7. Скрытый Launchpad опрашивается тогда и только тогда, когда есть незакрытый
   pending.
8. Projects показывает только имена каталогов слева и полный README справа.
9. README не может выполнить HTML/JS и не позволяет прочитать произвольный путь.
10. Sync показывает обе машины и остаётся проекцией `github-checker` через
    нормализованную read-model dispatcher.
11. Ошибка, stale или отсутствие данных нигде не отображаются как clean zero.
12. Содержимое Errors, Models, Contracts, Epics, Waits и Roadmap функционально
    не изменилось.
13. Неактивные экраны не опрашиваются каждые 10 секунд.
14. Все API, Node harness, Python, lint и typecheck gates зелёные.

## 14. Названные пределы и риски

| Риск | Последствие | Снижение |
|---|---|---|
| Незакрытая попытка запуска невидима с других вкладок | «launch outcome unknown» остаётся неразрешённым, оператор о нём не знает | фоновый опрос скрытого Launchpad, пока есть pending (§9.1); критерий 7 |
| Раскрытое подтверждение переживает возврат без проверки | оператор подтверждает запуск по устаревшему снапшоту | ре-валидация на возврате (§5.5) |
| Монолитный `<script>` завязан на глобальный DOM | скрытая вкладка ломает listener/render | сначала среда (§10), затем перенос блоков без правки их внутреннего HTML, затем развязка refresh |
| Снятие UI-входов Project detail | функциональность остаётся в API, но недоступна из UI | назвать в PR первой строкой; возврат — отдельное решение (§6.3) |
| README как XSS/чтение произвольного пути | исполнение недоверенного текста или утечка файлов | закрытый resolver + `<pre>` + лимиты размера и UTF-8 (§6.1) |
| Sync превращается во второго клиента github-checker | дрейф контрактов и расхождение verdict | только существующий `SyncService`/read-model (§7) |
| Launchpad как экран по умолчанию удлиняет холодный старт | первый экран ждёт `/api/launchpad` | немедленная загрузка при открытии + видимый маркер обновления |
| Колонка `Contract` в Roadmap молча пустеет после развязки refresh | таблица Roadmap теряет данные, которые сегодня приходят из `/api/contracts` | загрузчик Roadmap явно тянет `/api/contracts` (§9); harness-кейс на непустую колонку |
| Условная вкладка `Benchmarks` появляется/исчезает под оператором | активная вкладка пропадает из tablist | падение на `Launchpad` при исчезновении активной вкладки (§3.1) |
| Active-only polling показывает старые данные после возврата | оператор видит кэш | немедленный refresh при открытии вкладки + маркер «обновляется» |
